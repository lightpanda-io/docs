# Lightpanda Documentation

This repo is the Lightpanda docs site. It's a [Nextra 4](https://nextra.site) + Next.js 15 app. Content is MDX under `src/content/`, and the sidebar is driven by `_meta.ts` files. When writing or editing docs, your job is correct, tested, consistent pages that follow the house tone.

## Style and structure

Follow [STYLE_GUIDE.md](STYLE_GUIDE.md). It is the source of truth for tone, page types, page structure, links, and the checklist. Read it before writing or editing any page, then check your text against the writing pitfalls below.

The current docs are not the reference. Some pages are inconsistent or too verbose. Fix them toward the guide.

## Where things live

- `src/content/**/*.mdx`: the doc pages.
- `src/content/**/_meta.ts`: sidebar order and titles for each folder. A new page is invisible until it's registered here.
- `src/components/lightpanda/`: the site's own React components (navbar, footer, and the JSON-LD tags that describe each page to search engines).
- `redirects.mjs`: the single redirect map. The site is a static export, so `scripts/generate-redirects.mjs` also turns it into meta-refresh stub pages after the build.
- `src/content/reference/python.mdx` is generated by `scripts/generate-python-reference.py` from `lightpanda-python`. A daily workflow opens a PR when it changes. Do not edit it by hand.
- Diagrams and other images are not stored in this repo. Upload to `https://cdn.lightpanda.io/website/assets/images/docs/<filename>`, then reference with standard markdown image syntax: `![alt](url)`.

## MDX conventions

- Frontmatter is required: `title` (title case) and `description` (one sentence stating the outcome, includes the primary keyword, ~150-160 characters).
- Never use an unquoted colon (`: `) inside a frontmatter `description`. Plain YAML scalars break on it. Reword the sentence to avoid the colon.
- One H1 per page, matching the frontmatter title and including the primary keyword.
- Import Nextra components at the top, only if needed: `import { Tabs, Callout, FileTree } from 'nextra/components'`.
- Use `<Tabs items={[...]}>` with `<Tabs.Tab>` for parallel paths (npm/yarn/pnpm, Puppeteer/Playwright). Keep the tab set consistent across a page.
- Use `<Callout type="info">` for context and `<Callout type="warning">` for things that break if ignored.
- Use `<FileTree>` to show expected directory structure.
- Code blocks specify the language. Add `copy` to blocks the reader runs or pastes (` ```sh copy `, ` ```js copy `), not to output.
- Register every new page in the nearest `_meta.ts`, in the right order.
- When a page is moved, renamed, split, or merged, update `redirects.mjs`: add, retarget, or repoint old paths to the new page or anchor, including redirects that predate the change and already pointed at the now-stale path.

## Editing conventions

- Keep diffs minimal. Do not rephrase, reword, or reformat text that is not part of the requested change, even if a rewrite reads better. Removing genuine duplication is fine.
- Change existing metadata (titles, descriptions, frontmatter) only if needed.

## Writing pitfalls

Generated text has habits a reader spots quickly, and then they stop trusting the page. Check every page you write against these.

- **Don't mix things.** One idea per sentence, one claim per paragraph. A paragraph that bundles unrelated facts (a method's return type, its errors, and one argument's encoding) hides each one from a reader looking for one of them. Split by claim and put each fact next to what it describes.
- **Name the question each section answers,** in one sentence. If you cannot, delete the section. An inventory of what a product offers answers nothing, and it survives review because every sentence in it is correct.
- **Don't announce or recite.** No sentence saying what the page covers, no lead-in that recites the block below it ("Three plans cover the range…" above three plans), no transition pointing at what is on screen ("see the table below").
- **One name per thing.** A tool called `goto` stays `goto` on the whole page. Don't rotate synonyms.
- **Pronouns and references:** a pronoun has exactly one candidate in its sentence, and "this" or "that last point" always gets replaced by the thing's name.
- **Connectors assert a relation.** "however" means contrast, "so" consequence, "since" cause. Don't use one when the relation isn't there ("regardless of how you open a session", not "however you open a session").
- **Check absolute claims** ("never", "always", "only") against the rest of the page.
- **Plain words.** Pick the verb for what the reader does ("read", not "review"), write "is" instead of "serves as" or "stands as", and cut adjectives that imply a contrast the page doesn't make ("the main API" when there is one).
- **Behavior, not reassurance:** "Returns `null` if the key is missing", not "gracefully handles a missing key".
- **No negation for emphasis:** "not X, it's Y", "isn't just a wrapper", "No config. No setup." State the positive fact once.
- **No dramatic fragments** ("Fast. Deterministic."). Short sentences are fine; incomplete ones are not.
- **No marketing or filler words:** excited, powerful, seamless, robust, best-in-class, delve, leverage, utilize, comprehensive, streamlined, crucial, moreover, furthermore, notably, "it's worth noting".
- **No lists of three** used for rhythm. Restructure, or list what is really there.
- **No structure the content doesn't need:** a list for two sentences, bold in every paragraph, emoji bullets.

## Code snippets

Every code example must be complete, copy-paste ready, and tested against the version of Lightpanda, Puppeteer, or Playwright the page targets. Use `puppeteer-core` / `playwright-core` (they don't download Chromium). If you can't verify a snippet runs, don't include it. This applies to every commit that touches a snippet, including a one-line fix during review: re-run the snippet you changed, not the rest of the page.

To verify a page:
1. List every fenced block. Only runnable code (`js`, `ts`, `sh`) needs execution, not illustrative output.
2. When an example is split across several blocks or tabs, reassemble it into a complete file.
3. Run it in a scratch project outside the repo, with the exact packages and versions the page targets (`puppeteer-core`, `playwright-core`, `@lightpanda/browser`) and a Lightpanda instance started the way the page says.
4. Confirm it produces the result the page describes. Flag snippets you could not run (Cloud token, blocked target URL) instead of assuming they work.
5. After any later edit, re-extract and re-run the page's current content. A test of an earlier, similar script proves nothing about what is on the page now.

Python snippets use snake_case (`wait_for_selector`, not `waitForSelector`) to match each library's real API. Exception: JSON/wire-protocol dictionary keys (WebDriver BiDi commands, WebDriver capabilities like `webSocketUrl`) stay camelCase, since that's what the spec defines, not a Python identifier.

## Commands

- `npm run dev`: local dev server on port 1414.
- `npm run typecheck`: TypeScript check (`tsc --noEmit`).
- `npm run lint`: Next lint + Biome.
- `npm run lint-apply`: auto-fix lint and Biome issues.
- `npm run build`: static export to `out/`, then the pagefind index and the redirect stubs.

For now, only Biome works in a plain clone of this repo. The other commands need the website's repository, which provides shared packages.

Before finishing any docs change, run Biome, which is what CI runs. If the Biome in `node_modules` cannot read `biome.json`, run the version its `$schema` URL declares:

```sh
npx -y @biomejs/biome@$(grep -o 'schemas/[0-9.]*' biome.json | cut -d/ -f2) ci . --diagnostic-level=error
```

## Staying in sync with the codebase and demo

The docs describe external sources of truth. Check pages against them, not against other docs. Clone repositories read-only into a scratch directory outside this repo.

- Codebase: [lightpanda-io/browser](https://github.com/lightpanda-io/browser) (Zig). Authoritative for CLI flags, commands, CDP support, and the supported Web APIs.
- Examples: [lightpanda-io/demo](https://github.com/lightpanda-io/demo). Authoritative for runnable examples. Doc snippets should match the demo. Treat the demo as the source when they disagree.
- Python SDK: [lightpanda-io/lightpanda-python](https://github.com/lightpanda-io/lightpanda-python).
- Node.js package `@lightpanda/browser`: [lightpanda-io/node-packages](https://github.com/lightpanda-io/node-packages).
- Agent skill (`quickstarts/skill.mdx`): [lightpanda-io/agent-skill](https://github.com/lightpanda-io/agent-skill).
- Benchmarks (`core-concepts/benchmarks.mdx`): [lightpanda-io/agent-benchmarks](https://github.com/lightpanda-io/agent-benchmarks) and [lightpanda-io/demo](https://github.com/lightpanda-io/demo).
- Docker image (`run-locally/installation/docker.mdx`): [lightpanda/browser](https://hub.docker.com/r/lightpanda/browser) on Docker Hub.

Which source decides which page:

| Pages | Source of truth |
|---|---|
| `reference/cli/*`, `run-locally/commands.mdx` | `src/help.zon` for wording, `src/Config.zig` for whether a flag exists |
| `reference/mcp-tools.mdx`, `usage/mcp.mdx` | `src/browser/tools.zig` (`Tool.definition()`: `.description` and `.input_schema`), `src/mcp/tools.zig` (`extra_tools`) |
| `reference/pandascript.mdx`, `usage/pandascript.mdx` | `src/script/Runtime.zig`, `src/script/Schema.zig`, `src/browser/tools.zig` |
| `guides/use-python.mdx` | `lightpanda-python`, cross-checked against a live `pip install lightpanda` |

Known traps:
- Prose can lie, code decides. `help.zon` is hand-written: a flag it prints but `Config.zig` does not parse is not real, and a value `Config.zig` implements but `help.zon` omits is real. Tool `.description` strings and `src/script/skill.zig` go stale too: read the `exec<Name>` function or `Runtime.zig` to confirm behavior and return values.
- Diff MCP tool arguments against `input_schema` (`properties`, `required`), not only against `.description`.
- Check PandaScript claims in `src/script/`, not in the MCP tool code: the script runtime has its own `goto`, argument order and defaults.
- `lightpanda-python`'s `main` can be ahead of the published PyPI release. Document what `pip install lightpanda` gives today, and verify return types with a live call, not from docstrings.
- Compare against source, not against a locally built binary's `--help`, which can be stale.
- Never invent example output. Any log line or response shown must be captured from a real run.
- Explanation pages (Core concepts, Architecture) make structural claims: ownership, lifetimes, what is real versus stubbed. Verify them against the source.

Version policy. The docs mostly track the nightly build, so `main` is the default ref (the `nightly` tag points at the tip of `main`). Some hardcoded versions go stale, and the tag scheme changed from `vX.Y.Z` to `X.Y.Z` at 0.3. So each check must compare against `main` by default, fetch and check any version a page pins, and separately flag every hardcoded version string that is behind the latest release. Always report the exact ref (commit SHA and tag) compared against.

A drift check reports; it does not edit. Propose the specific change for each item and apply it only after confirmation.
